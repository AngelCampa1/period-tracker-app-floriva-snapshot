# Floriva 1.2.1 Release Plan

> Release identity: marketing version `1.2.1`, iOS build `20`, Android versionCode `20`.

## Goal

Ship the store-flow hardening already merged into the release branch so Annual,
Monthly, and Lifetime customers can enter, purchase, restore, switch, and retain
access through the intended native store flows. Preserve existing subscriber
plans, prices, renewals, and entitlements.

## Non-negotiable boundaries

- Build and sign locally. Do not use EAS Build or EAS Submit.
- Archive iOS with the normal `Floriva` scheme. Never archive with
  `FlorivaStoreKit`.
- Produce a locally signed Android AAB with the existing Play upload key.
- Capture a fresh screenshot set for 1.2.1; do not reuse 1.2.0 captures.
- Never print or commit Android signing secrets.
- Do not submit either store release until artifacts, automated billing safety
  gates, available native billing smoke tests, metadata, screenshots, and an
  independent review are complete.
- Store-backed checks that require an unavailable physical device, account
  state, or interactive store authentication must be attempted and recorded as
  blocked or not run. They do not become false passes, and they do not by
  themselves prevent submission when product configuration, entitlement
  safety, signed artifacts, and automated billing coverage are clean and the
  release owner accepts the recorded follow-up risk.
- If a release-blocking defect is found after creating build 20, increment the
  build/versionCode before rebuilding. Never overwrite or reuse a rejected
  artifact identity.

## Phase 1: Freeze and verify release source

1. Confirm the release branch contains the reviewed store-flow hardening.
2. Set every checked-in release source to `1.2.1` / `20`:
   - `package.json`
   - `app.config.ts`
   - `android/app/build.gradle`
   - `ios/Floriva.xcodeproj/project.pbxproj`
   - `ios/Floriva/Info.plist`
   - `scripts/check-release-env.js`
3. Update the release-config and preflight fixtures so drift fails CI.
4. Load `.env.production` and confirm the six product IDs remain:
   - `floriva.plus.monthly`
   - `floriva.plus.annual`
   - `floriva.plus.lifetime`
5. Run the app quality gates:

```bash
corepack pnpm lint
corepack pnpm typecheck
corepack pnpm test:ci --runInBand
corepack pnpm test:coverage:check
corepack pnpm test:imports
corepack pnpm test:smoke
```

## Phase 2: Fresh 1.2.1 screenshots and metadata

1. Build preview/release-equivalent native apps, not Expo Go or a development
   client.
2. Capture every required store frame again on iOS and Android for 1.2.1.
3. Review each frame for correct copy, clipping, privacy posture, and absence of
   prices in the public listing screenshots.
4. Regenerate every supported locale export from `floriva-marketing`:

```bash
corepack pnpm lint
corepack pnpm typecheck
corepack pnpm test
corepack pnpm check:assets
corepack pnpm render:store-docs
corepack pnpm export:assets
```

5. Verify App Store and Play export folders for `en`, `es`, `de`, `fr`, `ja`,
   `zh-Hans`, `pt`, and `ru` contain the new captures in the required order.
6. Keep the paywall screenshot private as subscription-review evidence only.

## Phase 3: Native billing verification and evidence

Run the deterministic billing suite, a local StoreKit transaction pass, and a
live store-console configuration audit before submission. Attempt the
store-backed account and device checks below wherever the available hardware,
account history, and authentication permit it.

Record each store-backed check as pass, fail, blocked, or not run. A blocked or
not-run check remains a post-submit follow-up and must never be described as a
successful native transaction. The 1.2.1 evidence record is
`docs/qa/2026-07-15-release-1.2.1-billing-evidence.md`.

### iOS sandbox/TestFlight

- Fresh install reaches onboarding and presents Annual first, Lifetime second,
  Monthly third.
- Annual and Monthly expose their one-month store introductory offer only when
  Apple considers the account eligible.
- Lifetime starts the eligible one-calendar-month app-level access period with
  no App Store transaction and no automatic charge.
- Annual and Monthly purchase completion unlocks the tracker.
- A purchased Lifetime product unlocks permanently.
- Restore purchases restores recurring and Lifetime access.
- Monthly-to-Annual and Annual-to-Monthly changes preserve access and take effect
  at the next renewal under the same subscription level.
- Cancellation save-offer redemption opens Apple redemption with the documented
  offer code copied and visible.
- Existing subscribers retain their plan, renewal, price, and entitlement.

### Google Play internal testing

- Fresh install reaches the same three-plan presentation.
- Annual and Monthly intro offers are visible only to accounts that have never
  had any Floriva subscription.
- Lifetime has no Play introductory offer; its eligible app-level access period
  creates no Play transaction or automatic charge.
- Purchase acknowledgement and entitlement refresh complete for all products.
- Restore/refresh recovers recurring and Lifetime ownership after reinstall.
- Both developer-determined retention offers redeem from the cancellation flow.
- Existing subscribers retain their base plan, renewal, price, and entitlement.

Record account, device, OS, build, product, result, and evidence for each
attempted gate. Do not use a production customer account for destructive
billing tests. Do not cancel or migrate a current subscriber merely to create
release evidence.

## Phase 4: Local signed artifacts

1. Load `.env.production` and ignored signing credentials without printing them.
2. Archive iOS locally to:
   `build/ios/Floriva-1.2.1-20.xcarchive`.
3. Export with `ios/ExportOptionsAppStore.plist` to:
   `build/release/AppStoreExport/Floriva.ipa`.
4. Confirm bundle `app.floriva`, version `1.2.1`, build `20`, distribution team
   `TEAMID1234`, release entitlements, and no embedded `.storekit` file.
5. Build Android locally to:
   `android/app/build/outputs/bundle/release/app-release.aab`.
6. Confirm package `app.floriva`, versionName `1.2.1`, versionCode `20`, and a
   valid upload-key signature.
7. Run `corepack pnpm release:preflight` only after both final artifacts exist.
8. Record SHA-256 hashes for the IPA, distribution summary, and AAB.

## Phase 5: Independent release review

Give a reviewer the release diff, focused test output, full quality-gate output,
fresh screenshot manifests, billing evidence (including explicit blocked and
not-run rows), artifact metadata, and hashes. Resolve every blocking or important
finding, rerun affected gates, and obtain a clean second review before merge.

## Phase 6: Store upload and submission

### App Store Connect

1. Upload the IPA through Xcode Organizer or Transporter.
2. Create/select version `1.2.1`, attach build `20`, and upload the fresh localized
   screenshots.
3. Paste `whats-new-1.2.1.md`, verify privacy/support URLs and reviewer notes, and
   confirm export compliance.
4. Confirm Monthly and Annual remain approved at the same subscription level,
   and Lifetime remains an approved non-consumable.
5. Add for review and submit only after the release owner confirms the final
   action.

### Google Play

1. Upload the signed AAB to a new production release for versionCode `20`.
2. Paste localized 1.2.1 notes and upload the fresh screenshot/feature-graphic
   exports.
3. Reconfirm the two intro offers and two retention offers remain active.
4. Resolve console errors, review the release, and roll out only after the release
   owner confirms the final action.

## Phase 7: Post-submit verification and tracker

1. Record App Store submission/build status and Play release status.
2. Recheck that the live product/offer configuration did not change during
   submission.
3. Update `~/Documents/Ventora Labs wind down/RECOVERY_EXECUTION_TRACKER.md`
   with build identities, artifact hashes, native billing evidence, submission
   IDs, statuses, and remaining blockers.
4. Push the reviewed release commit/branch only after repository verification is
   clean.
5. Monitor processing and review responses; if either store rejects the binary,
   preserve build 20 evidence and cut a new build number for the fix.

## Completion evidence

The release is complete only when source and artifacts agree on `1.2.1/20`, all
required pre-submit quality and billing safety gates pass, unavailable
store-backed checks are recorded truthfully with owner-accepted follow-up risk,
fresh screenshots are uploaded, both stores accept the release submission, and
the tracker records exact evidence.
